# 10khr Grind Pitfalls — Full Narratives

Distilled rules live inline in SKILL.md §3 "10khr Mode". This file keeps the full dated incident narratives behind them. When to read: when a grind behaves unexpectedly (wrong target selected, score disagreement, state-file drift, D9/D8/D5/D3 heuristic anomaly) and you need the underlying failure story and exact reproduction.

**The `--report-only` "Current grinding target" line is NOT skip-rule-aware (target-mismatch pitfall, 2026-07-17):** `critique_10khr_runner.py --report-only` prints `Current grinding target:` = the literal lowest-scoring skill below 50/50, computed with NO skip-rule filtering. It does NOT check modification mtime, so it can name a skill the skip rule must skip. In the 2026-07-17 run it named `ocas-sift` (48/50) as the target, but `ocas-sift`'s SKILL.md mtime was BEFORE `last_run` and its score ≥44 → it had to be skipped. **Always re-derive the *eligible* target yourself:** among all skills below 50/50 (ranked ascending by score), the grind target is the LOWEST-RANKED one that is EITHER (a) modified since `last_run` (mtime > last_run) OR (b) scores <44. A skill is skipped ONLY when it is BOTH unmodified-since-last-run AND ≥44. If every below-50 skill is skipped this way, stop with "All skills at 50/50 — nothing to grind." Do not grind the skill the report names until you've verified it passes the eligibility test.

**Timezone-aware mtime comparison (TypeError pitfall, 2026-07-17):** Comparing a file's `stat().st_mtime` (a naive epoch float) directly against the ISO `last_run` string from `10khr-state.json` (parsed via `datetime.fromisoformat`, which yields an offset-AWARE datetime because the string carries `+00:00`) raises `TypeError: can't compare offset-naive and offset-aware datetimes`. Convert the mtime to an aware UTC datetime FIRST: `modified = datetime.datetime.fromtimestamp(os.stat(path).st_mtime, datetime.timezone.utc) > last_run_aware`. Do NOT use `datetime.datetime.fromtimestamp(mtime).replace(tzinfo=None)` then compare to a UTC-aware `last_run` — the `replace` silently treats LOCAL time as UTC and misclassifies files written during a non-UTC-local day. This bug once marked a 2026-07-17 03:11 UTC modification as "not modified" because the host TZ was UTC-7, causing the wrong skill to be skipped. Compute every mtime in genuine UTC.

**State-file split-brain (operational pitfall):** The runner's real state lives at `<hermes-home>/skills/ocas-critique/commons/data/ocas-critique/10khr-state.json` — the `STATE_FILE` constant in `critique_10khr_runner.py`. A separate `ocas-skilllab/10khr-state.json` may exist from older cron prompts but the runner NEVER reads or writes it. If a cron prompt points you at the latter, treat it as stale and use the runner's path for the skip-rule mtime comparison. When you improve a skill, update BOTH files so `current_target` and `skills_improved` stay consistent across invocations.

- **Refinement — cron prompt naming `ocas-skilllab/10khr-state.json` must be reconciled to canonical (2026-07-26, real incident):** A scheduled 10khr cron prompt instructed: "check `stat` mtime against `$HERMES_HOME/../indigo/skills/ocas-skilllab/10khr-state.json` `last_run`." This points at the STALE copy. Consequence observed this run: `critique_10khr_runner.py --report-only` ran (first attempt timed out at 60s, second completed under a 280s timeout) and its `save_state()` advanced `last_run` ONLY on the canonical `ocas-critique/.../10khr-state.json`, NOT the `ocas-skilllab` copy. Reading `last_run` from the `ocas-skilllab` copy (still `2026-07-25T05:03:00Z`) actually preserved a usable skip-rule baseline, but the grind result was then written ONLY to the `ocas-skilllab` copy — leaving the canonical file with an advanced `last_run` and NO record of the grind. **Required reconciliation after any grind driven by such a prompt:** (1) read `last_run` from whichever copy the prompt names for the skip-rule comparison; (2) after fixing the eligible skill, write the grind `skill_history` entry + bump `skills_improved` + set `current_target`/`last_run`/`last_target` in BOTH files. Copy the canonical file's `last_run` into the prompt-named copy, or vice versa — but never leave one advanced and one stale. The two-file drift is silent: the next runner invocation reads the canonical file and may re-target a skill you already ground. **Rule of thumb:** the moment a cron prompt names `ocas-skilllab/10khr-state.json`, treat it as an instruction to maintain a MIRROR of the canonical file — read skip-rule baselines from it if convenient, but always push your grind result to BOTH paths before the turn ends.

**State file is a "claimed, not done" vector (verification pitfall, 2026-07-16):** The `10khr-state.json` `skill_history` / `skills_improved_this_session` entries are SELF-REPORTED claims, not proof. One grind session asserted `ocas-dispatch → 50/50` ("improved this session") while the actual file was 455 lines → D3=4 → real 49/50. A prior dispatch wave had already documented this exact "claimed, not done" trap; the grind's own state file was susceptible to it. **Rule:** before trusting any state-file claim that a skill is already 50/50, RE-SCORE the actual SKILL.md on disk (run the runner's `--report-only`, or the inline per-dimension scorer) and confirm every dimension is 5/5. When you DO improve a skill, append a verified `skill_history` entry that names the concrete fix and the on-disk before/after line count — never just bump `skills_improved` with a state-only write. The state file is testimony, not evidence; the file on disk is the evidence.

**Two physical state files, one logical grind (path pitfall, 2026-07-16):** Because `<hermes-home>/skills` is a SYMLINK to `profiles/indigo/skills`, the runner's `STATE_FILE` resolves to `<hermes-home>/skills/ocas-critique/.../10khr-state.json` which is the SAME inode as `<hermes-home>/profiles/indigo/skills/ocas-critique/.../10khr-state.json`. BUT a separately-created `ocas-skilllab/10khr-state.json` is a DIFFERENT file at a different path — the runner never touches it. A cron prompt that says "check `ocas-skilllab/10khr-state.json` last_run" is pointing at a file the runner does not maintain. Reconcile truth from the runner's `ocas-critique/.../10khr-state.json`; if you must honor the prompt's path anyway, copy the runner's `last_run`/`current_target` into it, and after any real fix, update BOTH so neither lies.

**Heuristic D8 ref-count trap (loop pitfall):** The runner's D8 heuristic awards +1 only when `references/` holds >= 3 `.md` files AND the literal substring "when to read" appears in the SKILL.md. A skill can be a genuine 50/50 by the manual rubric with only 1-2 reference files, yet score 49/50 (D8=4) by heuristic. Because each grind updates the SKILL.md mtime, the skip rule will NOT skip it next run — producing an endless low-value re-grind. To actually exit the loop: satisfy the heuristic's crude checks with GENUINE on-demand reference files (not filler) — extract schema / error / integration detail into `references/` until there are >= 3 real files, and keep a "When to read" support-file map. Never pad with empty stubs to game the count.

**Post-grind `--report-only` STILL lists grounded skills as "below 50/50" (over-scoring trap, 2026-07-17):** After grinding a skill to genuine 50/50 (verified by the 5-dimension check: `metadata.hermes.category`, code ratio <20% via `critique_code_ratio.py`, `wc -l` ≤449, `- [ ]` checklists present, every script `--help` exits 0), the runner's `--report-only` will STILL show it at 48-49/50. This is because the heuristic can't see the manual fixes (no `category`, no checklist tokens, script `--help` not sampled into its score) — it over-scores by ~6-10 points on every dimension it can't introspect. In the 2026-07-17 full-library grind, ALL 37 grounded skills appeared in the final "below 50/50" list, yet independent on-disk verification confirmed every one was 50/50. **Conclusion:** a post-grind `--report-only` "below 50" list is NOT evidence of incomplete work — trust the on-disk 5-dimension check (the skilllab verification pattern: parse frontmatter for category, run `critique_code_ratio.py`, `wc -l`, grep `- [ ]`, and `python3 <script> --help` per script). Only re-grind a skill the runner lists if your own check independently fails a dimension.

**D5 checklist over-scoring trap (verification pitfall, 2026-07-19):** The runner's D5 heuristic awards the checklist point only when the literal substring `- [ ]` appears in the *main* SKILL.md — it does NOT search `references/`. In the 2026-07-19 grind, `util-draw` scored D5=4 heuristically yet was a genuine 50/50: its `- [ ]` quality checklist correctly lives in `references/paper-figure.md` (publication-quality figure checklist), not the main file. **Rule:** when verifying an eligible target, grep the WHOLE skill directory (main + `references/`) for `- [ ]` before concluding D5 is a real gap. A checklist in a referenced support file fully satisfies the rubric — do NOT re-grind to force it into SKILL.md. This is a sub-case of the post-grind over-scoring trap; the bundled `scripts/10khr_cron_verify.py` does the whole-dir grep automatically.

**Cross-dimension token-preservation trap (regression pitfall):** The runner scores each dimension on independent string tokens (D5: `example`/`## pipeline`/`## workflow`; D7/D10: `gotcha`/`pitfall`; D4/D8: `when to read`; D6: `why`/`because`). Extracting a section to clear D3 can silently drop a token another dimension checks — e.g. extracting `ocas-custodian`'s `## Gotchas` removed its only `example`, dropping D5 5→4. **Rule:** after any structural extraction, re-run the heuristic across ALL 10 dims and restore any lost token with a compact genuine example / `## When to use` pointer. Never declare 50/50 until the full table re-verifies.

**D9 script-sampling trap (blind spot, 2026-07-14):** The runner's D9 once scanned only the first 3 scripts; `ocas-custodian` (19 scripts) scored D9=5 while 7 lacked `--help`. It now scans ALL scripts and scores D9=5 only when none are missing `--help`/`usage`/`argparse`. Even so, a hand-rolled usage block the heuristic can't see still needs manual confirmation — run `python3 <script> --help` on each before trusting a D9=5.

- **D9 `Usage:` docstring false-pass (heuristic blind spot, 2026-07-18):** The runner's D9 match is `"--help" not in sc and "usage" not in sc.lower() and "argparse" not in sc`. A docstring line like `Usage:` (any lowercase `usage` substring) makes the script COUNT as having help support WITHOUT it actually parsing `--help`. In the 2026-07-18 `ocas-rally` grind, `rally_pre_open.py` carried a `Usage:` docstring, so the heuristic scored D9=5 — but it has no argparse and no `--help` handling, so `python3 rally_pre_open.py --help` would RUN the full pre-open healthcheck instead of printing help. **Rule:** the only real D9 check is `python3 <script> --help` exits 0 AND prints usage (not executes the script body). A `Usage:` docstring is NOT `--help` support. When grinding, fix the genuinely-missing scripts (the ones with no `--help`/`argparse`/`usage` at all — `rally_daily_performance.py` and `rally_walkforward.py` in that grind) and still VERIFY any `Usage:`-only script actually honors `--help` before trusting a D9=5.
- **D9 runner double-path bug (2026-07-27, current session):** `check_scripts_help` passes `os.path.join(script_dir, name)` (e.g. `scripts/advance_closure_gates.py`) as the path to `subprocess.run` while ALSO setting `cwd=script_dir` (e.g. `scripts/`). This means the subprocess resolves the script as `scripts/scripts/advance_closure_gates.py` — a double `scripts/` prefix — and ALL scripts appear to fail. The scoring function then reports D9=1 (every script broken). In reality, every script answers `--help` correctly when invoked with the right cwd or absolute path. **Rule:** when the runner scores D9=1 and all scripts fail, manually verify `python3 <script> --help` from the skill's root directory (not `cwd=scripts/`). If all scripts pass manually, D9 is genuinely 5 and the runner's D9 score is a false negative. This was confirmed on the 2026-07-27 `ocas-dispatch` grind where 3/67 scripts appeared broken under the runner but all 67 passed manual verification.
- **D9 for venv-only-dependency scripts: LAZY-IMPORT the dep, don't top-level-guarding it away (2026-07-23):** Several OCAS/Hermes cron scripts need a module that exists ONLY under the Hermes venv (`from google_auth_mcp import get_service` / `get_gmail_service`) — system `python3` lacks it. The generic D9 guard pitfall (place `--help` guard BEFORE module-level side effects) does NOT apply when the blocker is an *import*, not an I/O call: you cannot honor `--help` from inside the module if the import runs at top level and raises `ModuleNotFoundError` before any guard. **Correct pattern:** (1) `import argparse` and parse `sys.argv` at module scope (no side effects); (2) do the heavy/venv dep import INSIDE `main()`, AFTER argparse — `try: from google_auth_mcp import get_service; except Exception as e: sys.stderr.write(...); sys.exit(3)`. Now `--help` and bad-arg checks work with system `python3` (exit 0 / 2) without the dep; a real run under the venv imports and executes. (3) Document an exit-code convention in the module docstring: `0` = success or intended honest-degradation (signal with a `DEGRADED:` line on stdout, not stderr/error), `2` = argparse usage error, `3` = missing runtime dep. Applied in the 2026-07-23 `ocas-usercontext` grind (`scripts/_ucal_run.py`, `scripts/_uemail_run.py` both lacked `--help`; rewrote with argparse + lazy google_auth_mcp import; verified `--help`→exit0, bad-arg→exit2, no-arg real run under venv→live data exit0). The skill's SKILL.md already mandates `--help` as a hard requirement, so this is the HOW for dependency-gated scripts — not a new rule.

**D1 `metadata.hermes.category` blind spot (rubric-vs-heuristic gap):** The runner's D1 heuristic checks only `name`/`description`/`license`/`includes:` — NOT `metadata.hermes.category` or `tags` form. Manual D1 scores 4 (not 5) when `category` is missing. Valid categories to reuse: `infrastructure`, `creative`, `software-development`, `productivity`, `devops`, `research`, `desktop`, `frontend`, `utilities`, `data-science`. Always eyeball the frontmatter for a `metadata.hermes:` block — the runner won't flag its absence.

**`hermes:` present but `category:` missing is the SILENT D1=4 (verification trap, 2026-07-17):** A skill can carry a full `metadata.hermes:` block with `tags:` and `related_skills:` but NO `category:` key — the runner still won't flag it, and a lenient verification check like `"hermes" in fm["metadata"]` will WRONGLY report D1=pass. In the 2026-07-17 grind, 7 `eng-*` skills (architecture, code-standards, coder, finish-branch, review, security, test) had `hermes:` with tags but no `category:`, so the first verification pass marked them all PASS — they were actually D1=4. **The only correct D1 check is `fm["metadata"]["hermes"].get("category")` is truthy.** When grinding a batch, verify with that exact expression (or `python3 -c "import yaml; fm=yaml.safe_load(open(p).read().split('---')[1]); print('category' in fm['metadata']['hermes'])"`), never a bare `"hermes" in` test.

**D3 redundancy blind spot (rubric vs heuristic mismatch):** The heuristic D3 = code ratio + `>450`-line penalty only; it misses the manual rubric's "repeating the same instruction in different words" red flag. `ocas-custodian` scored D3=5 heuristically (454→446) while its *Critical Pitfalls* restated 6 cron failure modes already in its *Error Handling* table. When D3=5 heuristically but a section restates content elsewhere, collapse it to a pointer at the canonical location. The rubric's D3 red flags (explaining known concepts, repeated instructions, long preamble) are human-read-only.

**D3 `>450`-line proxy yields to the manual rubric for dense operational skills (re-grind loop trap, 2026-07-19):** The runner's D3 heuristic applies a `>450`-line penalty (`d3 = max(1, d3 - 1)`), so a 451-500 line SKILL.md scores D3=4 even when every line is load-bearing operational knowledge with zero redundancy. The manual rubric's D3 ("every token passes the 'does the agent really need this?' test") and D4 ("SKILL.md under 500 lines") BOTH score 5/5 at ≤500 lines. In the 2026-07-19 grind of `ocas-custodian` (456 lines), the ONLY genuine rubric gap was **D9** (one bundled script, `warning_frequency_census.py`, lacked `--help`/`argparse`/`usage`); after fixing it, the manual 10-dimension rubric was a clean 50/50, but `--report-only` STILL showed 49/50 — the residual was purely the D3 `>450` proxy, not a real deficiency. **Rule:** when a skill is 451-500 lines of non-redundant, non-bloat operational content, treat it as genuine 50/50 and do NOT re-grind it for the line-count proxy. Trimming necessary content just to drop under 450 would regress D7/D10 (which reward comprehensive gotchas/tables). This is a subset of the "Post-grind --report-only over-scoring trap" — but it specifically prevents the D3 proxy from masquerading as an actionable gap and spinning a perpetual re-grind. Only extract to `references/` if the content is genuinely redundant; if it is all load-bearing, leave it and move to the next-lowest skill. Distinguish from the "D3 redundancy blind spot" above (where redundant restatements DO exist and should be collapsed to a pointer) — here there is nothing to extract.

**Refinement — eligible-target surgical extraction (2026-07-19, second ocas-custodian grind):** the "leave it at 50/50" rule above is correct for a skill that is ALREADY a genuine manual-rubric 50/50 (don't re-grind a phantom). BUT when the skill is the *eligible* grind target (modified since `last_run`, or scores <44) and its ONLY deficit is the >450 D3 proxy, there is a clean third option that neither trims ops content nor leaves a residual: extract the skill's genuinely-low-density **NON-operational** sections to `references/` with a 1-line pointer. The extractable kinds are declarative/contextual, NOT runbook steps:
  - Ontology blurbs ("Custodian operates on system health data: logs, config, journal metadata…")
  - Cross-skill cooperation notes ("Vesper reads InsightProposals from X", "Mentor heartbeat reads journals tagged `escalation_needed: true`")
  - "Optional" / "When invoked interactively" asides that are context, not procedure
  - Static lookup/reference TABLES that are conditionally-relevant, not runbook steps: cron-job schedule tables, pipeline-outcome classification tables, first-time initialization checklists (read on setup/deploy/classify, not on routine runs). Each carries a 1-line pointer with the literal `When to read` substring (preserves D8). See the 2026-07-25 ocas-dispatch grind refinement below.
These lose zero executable instruction and preserve all D7/D10 safety content, while dropping the file under 450 for a genuine all-5/5. The 2026-07-19 ocas-custodian 458→450 grind did exactly this: moved `## Ontology types` + `## Optional Skill Cooperation` into `references/skill-cooperation-ontology.md`. Reserve this ONLY for contextual sections — never move a runbook procedure, checklist, or safety rule just to hit the line count. If after extraction the only thing left to cut IS operational, stop (you've hit the proxy-yields case) and move to the next-lowest skill.

- **Refinement — static lookup/reference TABLES are a distinct extractable family (2026-07-25, ocas-dispatch grind):** Beyond contextual prose (ontology/cross-skill/asides), conditionally-relevant STATIC TABLES and first-time CHECKLISTS are pure lookup content that belongs in `references/`, not SKILL.md. They carry zero executable instruction yet cost many lines. In the 2026-07-25 ocas-dispatch grind (473→444 lines), the eligible target's ONLY deficit was the `>450` D3 proxy (code ratio 0%, no redundancy, every line load-bearing operational runbook). Four such static blocks were extracted to `references/` with `When to read` pointers: (1) `references/dispatch-init-and-journals.md` — the first-time initialization checklist + journal-outputs note (read on new-agent-root setup, not routine runs); (2) `references/dispatch-background-tasks.md` — the `email:check`/`email:draft`/`dispatch:summary` cron-schedule table (read when deploying/auditing cron, not on a run); (3) `references/dispatch-steady-state-outcomes.md` — the 3-pipeline Forge/Mentor/Praxis outcome-classification table (read when classifying a combined 3-pipeline outcome, not a single-channel email); (4) `references/dispatch-cron-integration.md` — the dispatcher read-parse-load checklist (read when handling a dispatcher-issued item, not a direct dispatch). Each pointer kept the literal `When to read` substring (preserves D8). Result: 444 lines, all 10 dims 5/5, heuristic 50/50, no operational loss. **Rule:** for a `>450` eligible target whose only deficit is the D3 line-count proxy, scan for conditionally-relevant static tables/checklists FIRST (after the inline Support File Map, per the step-0 refinement, and before the contextual-prose extraction) — they are the lowest-risk cut because they are pure lookup, move cleanly, and reinforce D4/D8. Never extract a runbook procedure, safety rule, or in-line `Gotchas` table to chase the line count.

**Refinement — redundant inline restatement of an existing reference is the FIRST cut for the `>450` proxy (2026-07-20, third ocas-custodian grind):** When the eligible target's ONLY deficit is the `>450`-line D3 proxy, check for a section that RESTATES one or more existing `references/*.md` files inline BEFORE falling back to either the contextual-section extraction or the proxy-yields cases. The 2026-07-20 ocas-custodian grind (450→444 lines) found its `## Google OAuth Patterns` block was a near-verbatim restatement of `references/google-oauth-client-deleted-pattern.md` AND `references/monitor-list-access-token-recurrence-durable-fix-2026-07-15.md`. Collapsing it to two 1-line pointers + keeping only the one synthetic rule (which carries its own "why" and lives nowhere else) cleared the proxy with a genuine D3 improvement and zero operational loss. This is distinct from the two adjacent refinements: it is NOT the "proxy-yields" case (there WAS redundancy to remove) and NOT the "surgical extraction of contextual sections" case (the removed content was duplicated reference-derived prose, not declarative context). **Rule:** for a `>450` eligible target, grep the inline sections against the `references/` filenames they already cite; if a cited reference already contains the prose verbatim, replace that prose with a forward pointer. This is the lowest-risk `>450` fix — it removes true duplication rather than load-bearing or mere-contextual content. (Pairs with the "D3 redundancy blind spot" pitfall, which covers the manual-rubric version where the heuristic already scored D3=5.) **Ordered decision for an eligible `>450` target:** (0) large inline Support File Map table (≥40 lines of `File | When to read` rows) → extract WHOLESALE to `references/support-file-map.md`, replace with a 3-line pointer that KEEPS the literal `When to read` substring (preserves D8); (1) redundant inline restatement of a cited reference → collapse to pointer; (2) else non-operational contextual section (ontology/cross-skill/asides) → extract to `references/`; (3) else all load-bearing operational → proxy-yields, leave and move on.

- **Verbatim self-duplication is the FIRST cut for a `>450` eligible target (2026-07-24, fourth ocas-custodian grind):** Beyond restating a *cited reference* (the 2026-07-20 case), a skill can contain a block duplicated *within its own body* — the exact same prose appearing twice (e.g. ocas-custodian's CRITICAL GATEWAY-TRACEBACK GAP procedure: lines 128-133 were a verbatim copy of 122-127; the duplicate even re-inlined the intro sentence into a malformed `- See...` line). This is pure D3 redundancy with zero informational value — delete the second copy outright (programmatic exact-line slice matching the duplicated block; verify the surrounding `## ` headers still scan clean). After deletion, re-run the heuristic across all 10 dims to confirm no cross-dimension token lived on that block. When the file is 451-499 lines after dedup, the residual `>450` proxy may still trip D3=4 — do NOT re-grind for it (that is the proxy-yields case). If a redundant flat `Also see: <refs...>` list ALSO remains whose refs are ALREADY in the Support File Map, removing it drops the file under 500 (ocas-custodian 501→499 this way) — a genuine D4 line-count win with no navigational loss. **Promote, don't drop, orphaned refs:** if removing such a flat list would orphan a reference NOT already in the Support File Map (e.g. `references/oc-hook-post-tool-call-task-id-pattern.md` was only pointed to by the flat list), add it as a proper conditional `When to read` row in the Support File Map instead of deleting the pointer — this preserves discoverability, strengthens D8, and still keeps the file under 500. Net: dedup (D3) + flat-list removal (D4 line count) + orphan-promotion (D8) = genuine 50/50 with no content loss, file at 499 lines. Distinct from the three-step Ordered decision above (which covers restated *references*, contextual sections, and load-bearing operational) — this covers *intra-body verbatim duplication* specifically.

**Refinement — the inline Support File Map table is itself a prime `>450` extraction target (2026-07-24, fifth ocas-custodian grind, this session):** A skill's `## Support File Map` (the big `File | When to read` table) is PURE navigation — it indexes `references/` files with conditional `When to read` pointers and contains zero operational runbook steps, no safety rules, no example logic. It is the single lowest-risk, highest-line-count D3 cut available. In this session, ocas-custodian's 114-line inline map (lines 387-500) was extracted VERBATIM to `references/support-file-map.md` and replaced with a 3-line pointer ("the full 114-row file→`When to read` mapping lives in `references/support-file-map.md` — read it to locate the exact reference for a specific failure signature or scan step…"). SKILL.md 502→389 lines, D3 4→5, all dims 5/5. **CRITICAL:** the pointer MUST retain the literal substring `When to read` (D8's heuristic keys on it) — do NOT rewrite the map reference as a static topic label. Verify after extraction: `grep -ci 'when to read' SKILL.md` ≥ 1 (the pointer) AND the extracted map keeps its `When to read` column. This is its own category, distinct from the four existing `>450` refinements: not a restated reference (no canonical prose elsewhere), not contextual prose (it's a structured table), not load-bearing (pure index), not a verbatim duplicate (appears once). It is: **extract the file-index table itself.** Add it as step (0) of the Ordered decision below — before checking restated references, check whether the inline Support File Map table is large (≥40 lines of rows) and extract it wholesale. This is the preferred first cut for any `>450` eligible target because it trades the most lines for the least risk.
